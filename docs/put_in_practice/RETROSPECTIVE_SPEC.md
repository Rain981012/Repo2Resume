# Put-in-practice 复盘结构规范

> **本文件是后续所有 `docs/put_in_practice/**/*.md` 复盘的强制结构标准。**  
> 范本：`PhaseB/03_phase_2_5_lifecycle_hooks.md`、`PhaseB/04_phase_3_retrieval_jobs.md`。  
> Agent / 人工写复盘时：先读本规范，再写或查漏补缺；禁止另起一套目录。

---

## 0. 文档目标与原则

| 原则 | 说明 |
|------|------|
| 用途 | **面试复习稿**，不是产品 README、不是 changelog |
| 增量 | 已有文档只查漏补缺，**禁止整篇重写**抹掉旧坑/旧知识点 |
| 范围 | 一次只服务用户点名的本步；未做的不要标成 ✅ |
| 可讲 | 每节都要能直接变成面试口述；少空话，多「本项目落点」 |
| 对齐代码 | 路径、模块名、验收现象以仓库现状为准 |

**命名与路径**

- Phase A → `docs/put_in_practice/PhaseA/`
- Phase B → `docs/put_in_practice/PhaseB/`
- 文件名：`{序号}_phase_{id}_{短名}.md`（例：`05_phase_4_resume_subagent.md`）
- **新建前先问用户确认文件名**；默认优先改已有文档

**标题格式**

```markdown
# Phase {A|B} / Phase {id} 实践复盘：{标题}（面试复习稿）

> 项目：Repo2Resume  
> 阶段：Phase {id} — {一句话阶段名}  
> 对应：`MVP_PLAN.md` Phase {id}；前置 `{上一篇文件名}`  
> 验收日：YYYY-MM-DD（可选；有真跑再写）
```

## 1. 强制目录（六大块 + 可选 1.5）

每篇复盘**必须**包含下列一级标题（编号与文案保持一致）：

```text
## 1. 一句话定位
## 1.5 {本阶段}的完整流程          ← 强烈建议；机制/流水线阶段必写
## 2. 本阶段完成了什么（对照计划）
## 3. 做法 · 影响 · 亮点 · 踩坑
## 4. 本阶段知识点（面试向）
## 5. 下一步
## 6. 30 秒速记卡
```

Skill 要求的「三块核心」映射：

| 用户关心的三块 | 落在章节 |
|----------------|----------|
| ① 完成了什么 | §2 |
| ② 做法 · 影响 · 亮点 · 踩坑 | §3 |
| ③ 面试知识点 | §4 |

## 2. 各节写法细则

### §1 一句话定位

- 3–6 句内说清：本阶段**解决什么问题**、**核心手段是什么**、面试可怎么开场。
- 可点名 1–2 个手写/关键模块，不要列清单（清单放 §2）。

### §1.5 完整流程（强烈建议）

面试讲清「怎么搭」和「怎么跑」，比只背概念更有说服力。按阶段类型选子节（可增减，但逻辑顺序固定）：

| 子节 | 何时写 | 写什么 |
|------|--------|--------|
| **A. 构建 / 注册顺序** | 几乎总要 | ASCII 依赖链：模块①→②→…；附「为什么这个顺序」 |
| **B. 运行时 / 端到端用户流程** | 几乎总要 | 用户一句话 → Agent/CLI → 内部调用链 |
| **C. 核心内部流水线** | 有独立子系统时 | 如 RAG 内部、一次 `registry.call`、Writer-Critic |
| **D. 并列能力线** | 有第二条腿时 | 如「职位匹配 vs 检索」 |
| **E. CLI 对照** | 有非 chat 入口时 | 不经过 loop 时怎么跑 |
| **F. 数据落在哪** | 几乎总要 | 表 / 文件 / 缓存一览 |
| **G. 刻意没做 / 没接主流程** | 有明确砍掉项时 | 避免面试被问「为什么没有 X」时含糊 |

机制类阶段（如 hooks）侧重 **A 挂载顺序 + B 单次调用 + C 与 loop 关系 + F 数据**。  
能力类阶段（如检索+职位）侧重 **A 构建 + B 用户路径 + C/D 流水线 + F/G**。

### §2 本阶段完成了什么（对照计划）

必须包含：

1. **对照表**：Step / MVP 项 | 交付物 | 状态（✅ / ⚠️ 部分 / ❌ 未做）
2. **交付物路径**：源码、提示词、测试、文档的真实路径列表
3. **验收一句**：测了什么、真跑现象或「仅单测绿、真跑未做」

区分：**搭建完成** vs **验收/真跑尚未做**。

### §3 做法 · 影响 · 亮点 · 踩坑

固定四个二级标题（编号保持）：

```markdown
### 3.1 做了什么
### 3.2 对项目的影响
### 3.3 亮点（可上面试）
### 3.4 踩坑
```

| 小节 | 要求 |
|------|------|
| 3.1 | 具体动作（手写了哪段、改了哪条规则、接了哪个工具），可 bullet |
| 3.2 | 对行为 / 后续 Phase / 验收标准的影响（可用表） |
| 3.3 | 1–4 条设计点；每条能变成面试「我为什么这样设计」 |
| 3.4 | **新坑只追加、不删旧坑**；格式见下 |

**踩坑推荐格式**

```markdown
**坑 N：{短标题}**  
- 现象：…  
- 原因：…  
- 教训：…  
- （可选）面试升华：…
```

或表格：`| 坑 | 现象 | 教训 |`。可与前序 Phase 文档交叉引用。

### §4 本阶段知识点（面试向）

#### 4.0 开篇：五问模板（强制声明）

每篇 §4 开头必须写明（可复制）：

```markdown
每个技术点按**同一套五问**答（临场可直接套）：

1. **X 是什么？**
2. **为什么要在 Repo2Resume（这个项目）里用它？**
3. **为什么不用……（更偷懒 / 更常见的替代做法）？**
4. **有什么优缺点？**
5. **为什么不用其他同类技术 / 竞品？**
```

可选：先放一张「技术点 → 本项目落点」总表，再逐条展开。

#### 4.1 每个技术点正文（强制五问体）

```markdown
### ① {概念名}

**1. 是什么？**  
…

**2. 为什么要在这个项目用它？**  
…

**3. 为什么不用「……」？**  
…

**4. 有什么优缺点？**  

| 优点 | 缺点 |
| ---- | ---- |
| … | … |

**5. 为什么不用其他同类技术？**  
…
```

选型原则：优先写本阶段**真实做过决策**的点（手写模块、换过的模型、砍掉的方案），少写空泛百科。

#### 4.2 速记对照表（强制）

§4 末尾一张表：

| 我用了 | 为什么不用常见替代 | 一句话 |
|--------|--------------------|--------|
| … | … | … |

工程取舍（卡死检测、懒加载等）也可套同一五问，可放在「补充」小节。

### §5 下一步

- 未完成 / 可选打磨 / **下一 Phase 入口**
- 若已有下一篇复盘，链到文件名
- 不要把「计划里以后才做的」写成已完成

### §6 30 秒速记卡

极短 bullet，建议固定槽位：

- **做了什么**
- **Gate / 验收**
- **一句话**
- **面试答法**（可写「见 §4」）
- **流程**（可写「见 §1.5」）
- **踩坑**（点名 2–3 个）
- **下一站**

## 4. 增量更新（已有文档）规则

1. **先读后写**目标文档全文（或相关章节）
2. 列出：已有 / 缺失 / 过时（可对用户简报）
3. 只改本步相关：
   - 更新 §2 状态表与交付物
   - §3.3 / §3.4 **追加**亮点与坑 N
   - §4 **追加**技术点或补全未写满的五问
   - 改 §5 / §6
4. **禁止**：删旧坑、整文件换模板、把未做项标 ✅
5. 改完用 3–5 条 bullet 告知用户改了哪些节

## 5. Agent 操作清单

```text
1. 读本规范 RETROSPECTIVE_SPEC.md
2. 确认本步范围 + 目标路径（新建则先问文件名）
3. 若新建：复制 §3 骨架，按 §2 细则填满（尤其 §1.5 与 §4 五问）
4. 若增量：按 §4 查漏补缺
5. 对照代码/对话核对路径与验收现象
6. 回告：改了哪些节 + 建议下次触发语
```

触发语示例：

```text
更新 put_in_practice：我完成了 Phase 4 贡献归属，按 RETROSPECTIVE_SPEC 查漏补缺
新建 Phase 5 复盘，严格按 docs/put_in_practice/RETROSPECTIVE_SPEC.md
把 05 的 §4 补成五问体
```
