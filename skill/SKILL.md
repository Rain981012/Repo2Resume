# Repo2Resume：从本地代码到定制简历

读取用户本地 git 仓库的个人贡献，汇总技能画像，按画像搜索并推荐职位，
再针对用户选定的 JD 从仓库事实中提炼亮点，经讨论后导出 Markdown 简历。

阶段 A **明确不做**：独立 CLI harness、向量库/RAG 运行时、自研多智能体框架（那些是阶段 B）。

全程遵守底部的事实清单规则。三个 ⏸ 为必须停下等待用户确认的节点。

```
进度清单:
- [ ] Step 1 分析仓库 → 统计 JSON
- [ ] Step 2 技能画像 ⏸ 用户确认
- [ ] Step 3 职位搜索与打分 ⏸ 用户选定目标
- [ ] Step 4 生成项目经历草稿 → 自我审稿
- [ ] Step 5 与用户迭代修改 ⏸ 确认后导出
```

## Step 1: 分析仓库

1. **确定仓库路径**（用户未指定时按优先级自动发现，可再请用户增删）：
   1. 先读本仓库下 `test_repos/` 内的 git 仓库；
   2. 再读与 Repo2Resume 同级目录下的其他 project（已在 `test_repos/` 中出现过的路径不要重复分析）；
   3. 若以上皆空，询问用户自行提供仓库路径。
2. **确定 author**：询问用于过滤的 git 作者名/邮箱（可多个）。
   多人仓库必须用 `--author` 只统计用户本人；多邮箱多次传入 `--author`。
   不确定时，对目标仓库执行 `git -C <repo> shortlog -sne`，列出作者供用户辨认。
3. **执行统计脚本**（不要自己重写分析逻辑）：

```bash
python3 scripts/git_stats.py <repo1> <repo2> ... \
    --author <email或名字> [--author <第二个身份>] \
    --output runs/<YYYY-MM-DD>/stats.json
```

4. **异常处理**（处理完毕前不得进入 Step 2）：
   - `errors` 非空：逐条向用户报告失败路径与原因（如不是 git 仓库），请用户修正后重跑脚本。
   - `warning`（如缺少 README，但有源码/依赖文件）：可继续分析，结束时告知用户依据源码完成分析即可。
   - `author_commits == 0`：说明当前 `--author` 未命中任何 commit。展示该仓 `git shortlog -sne`，请用户确认/修改 author 后**重跑脚本**；严禁脑补该仓库的贡献。

## Step 2: 技能画像 ⏸

- **读取** [prompts/01_skill_profile.md](prompts/01_skill_profile.md)
- **输入** Step 1 的 `stats.json`
- **输出** 结构化画像（字段由 01 提示词定义）

**必须展示并请用户确认**（至少：主方向）；**未确认不得进入 Step 3**。`gaps_or_cautions` 建议展示，但不强制确认——用户可稍后自行补充。展示内容包括：

1. 每个 repo 的技术栈（语言、框架、数据库等）。
2. 主方向：前端/后端/全栈？Agent 应用 vs 传统开发？应用开发 vs 算法？
3. 基于 commit 的主要贡献：每仓 4–5 条要点（可附两三句说明），尽量给出代码/统计出处。
4. 每个 project 的一句话总结（产品/业务定位）。
5. **方向探索（不是投递清单）**：根据画像给出 4–8 个概括性目标职位类型
   （如：Python 后端工程师、Django 开发、AI Agent 应用开发），每条一句话说明为何匹配。
   - 只给 title + 理由；**不**给具体公司；**不**联网抓取真实 JD。
   - 供用户建立「可以往哪投」的直觉；用户可增删方向后再进 Step 3。
   - 真实在招岗位的搜索与打分在 Step 3 完成。

## Step 3: 职位搜索与打分 ⏸

- **读取** [prompts/02_job_search.md](prompts/02_job_search.md)
- **先问** 目标地区/城市 / 远程 / 职级；以及特殊要求（是否应届、目标薪资、学历硬性门槛等）。
  例如用户为本科学历，则不要推荐硬性要求硕士/博士的岗位。
- **再问两类语种偏好**（二者独立，均可与 `coding_language` 不同）：
  1. **`job_search_locale`（搜岗用语种/市场）**：决定用什么语言搜、优先哪些招聘站。
     - **默认 `zh-CN`**：中文搜索词 + 中文站点（Boss 直聘、智联、拉勾等），面向中国大陆岗位。
     - **可改**：用户可显式改为 `en`（LinkedIn、Indeed 等英文站）或其它 BCP-47 码；字段须始终写入本轮偏好，便于以后扩展市场。
     - Step 3 开头可简述默认并询问是否改；用户未改则按 `zh-CN` 开搜。若与「目标地区」明显冲突（如地区=多伦多但仍为 `zh-CN`），先确认再搜。
  2. **`resume_locale`（简历用语种）**：供 Step 4 写作与导出；可与搜岗语种不同。进入 Step 4 前必须有值（可默认跟 `job_search_locale`，但须让用户有机会改）。
- **执行**：按 02 与 `job_search_locale` 生成搜索词并选站 → 联网搜索真实在招职位 → 打分排序；也接受用户粘贴 JD。
  - 至少搜索 **≥20** 个真实在招岗位（优先近三个月发布）；
  - 按 JD 与 Step 2 方向/画像的匹配度打分，向用户展示评分最高的 **5** 个。

**⏸ 用户选定 1 个（或多选）目标职位** 后才进入 Step 4。

## Step 4: 生成项目经历草稿 + 自我审稿

1. **读取** [prompts/03_resume_writing.md](prompts/03_resume_writing.md)。
2. **现阶段只输出可复制的 Markdown 项目经历**（不要完整简历：不写姓名/联系方式/技能总表/教育/工作经历）。
   每个入选项目固定三块：
   - **项目名**（仓库名或概括性业务名）
   - **一句话项目总结**
   - **项目经历** bullet（高度吻合且充实 → 4–5 条；相关较少 → 至少 2 条；无证据不硬凑）
   例如 JD 要求 Redis 等缓存中间件，则应在仓库中定位相关证据，写成可溯源的 bullet（`<!-- src: 仓库, 依据 -->`）。
3. 草稿完成后立即按 [prompts/04_critic_review.md](prompts/04_critic_review.md) 自查；审稿–修订最多 **2** 轮。  
   完整简历模板 `templates/resume.md.j2` 留待后续阶段再套用。

## Step 5: 迭代修改与导出 ⏸

1. 展示草稿 Markdown，按用户意见修订。
2. 新数字必须来自 `stats.json` 或用户亲口提供。
3. **⏸ 用户确认定稿** 后写出：`runs/<YYYY-MM-DD>/resume_<公司或职位>.md`。
4. 询问是否删除 `<!-- src -->` 溯源注释；**投递版默认删除**，存档版可保留。

## 归档（每轮跑完 Step 5 后执行）

把本轮产物写入 `runs/<YYYY-MM-DD>/`（同日多轮用 `runs/<YYYY-MM-DD>-<HHMM>/` 避免覆盖）：

| 文件 | 内容 |
|---|---|
| `stats.json` | Step 1 的 git 统计输出 |
| `skill_profile.json` | Step 2 确认后的技能画像 |
| `job_directions.md` | Step 2 概括性职位类型（若有） |
| `jobs_ranked.json` | Step 3 搜索与打分结果（可只保留 top 列表） |
| `target_jd.md` | 选定职位的 JD 全文或摘要 + 来源链接 |
| `resume_draft_v*.md` | 各版**项目经历**草稿（现阶段非完整简历） |
| `resume_final.md` | 用户确认的项目经历定稿（或后续完整简历） |
| `user_feedback.md` | 用户修改意见摘要（按轮次） |
| `meta.json` | 本轮元数据（见下） |

`meta.json` 最小字段：

```json
{
  "model": "本次使用的模型名",
  "date": "ISO 日期或本地日期时间",
  "target_job": "选定职位标题 + 公司（若有）",
  "resume_locale": "zh-CN | en | …（简历用语种）",
  "job_search_locale": "默认 zh-CN；可改为 en 或其它（搜岗市场/站点）",
  "repos": ["分析过的仓库路径或名称"],
  "authors": ["使用的 --author 过滤"]
}
```

`runs/` 含个人简历与联系方式，已在 `.gitignore` 中，不要提交到远程。

## 事实清单规则（全程最高优先级）

1. 贡献相关数字与技术证据默认以 `stats.json` 为准。口述只补充统计中没有的信息（如教育、联系方式，或用户亲口给出的指标）。若口述与统计冲突（例如自称精通 Django 但无任何相关仓库证据），必须先询问用户；用户坚持口述可以记录，但不得默默覆盖或假装有仓库证据。
2. 拿不准就问用户，不擅自美化。
3. 禁止编造事实与虚构成果（用户量、性能百分比、营收、团队规模等，统计没有且用户未亲口提供则不写）。
4. 多人仓库只写用户本人 commit 对应的贡献；不得把他人工作写进简历，除非用户明确要求并知情。
5. 不得擅自修改用户仓库；任何高危操作（写文件到仓库内、强制操作等）必须事先征得同意。
6. 写作时每条项目 bullet 必须带 `<!-- src: 仓库, 依据 -->`；投递导出前按 Step 5 处理是否删除该注释。
