# Repo2Resume:从本地代码到定制简历

> **权威流程以仓库根下 [`../SKILL.md`](../SKILL.md) 为准**；本文件仅为 prompts 目录内速览，若与根 SKILL 冲突以根 SKILL 为准。

五步流程,三个必须停下等用户确认的节点(标注 ⏸)。全程遵守底部的事实清单规则。

```
进度清单:
- [ ] Step 1 分析仓库 → 统计 JSON
- [ ] Step 2 技能画像 ⏸ 用户确认
- [ ] Step 3 职位搜索与打分 ⏸ 用户选定目标
- [ ] Step 4 生成简历草稿 → 自我审稿
- [ ] Step 5 与用户迭代修改 ⏸ 确认后导出
```

## Step 1:分析仓库

1. 询问用户(如果未提供):要分析哪些仓库路径?git 作者名/邮箱是什么(可多个)?
   - 用户不确定邮箱时,先运行 `git -C <repo> shortlog -sne` 列出所有作者供其辨认。
2. 运行统计脚本(**执行**,不要自己重写分析逻辑):

```bash
python3 scripts/git_stats.py <repo1> <repo2> ... --author <email> --output runs/<今天日期>/stats.json
```

1. 读取输出 JSON。注意 `errors` 与 `warning` 字段:某仓库作者 commit 为 0 时,向用户核对邮箱拼写而不是跳过。

## Step 2:技能画像 ⏸

按 [prompts/01_skill_profile.md](prompts/01_skill_profile.md) 把统计 JSON 汇总为结构化画像。

**⏸ 展示画像并逐条确认**,重点让用户核对主方向、分类后的 `tech_stack` 和 `caution`。用户修正后更新画像再继续。

## Step 3:职位搜索与打分 ⏸

按 [02_job_search.md](02_job_search.md):确认城市/远程/级别/`top_n`(默认5,最多10) → 生成搜索词(含大厂专项) → 网络搜索真实在招职位(**≥50**) → 一套综合 Top-N → 询问是否继续搜更多。用户也可直接粘贴 JD 参与打分。

**⏸ 用户选定目标职位**后继续。

## Step 4:生成简历草稿 + 自我审稿

1. 按 [03_resume_writing.md](03_resume_writing.md) 写**仅项目经历**(严格 STAR、每条2–4句；正文禁止占比/commit 数/免责声明)。现阶段不要套完整简历模板。
2. 草稿完成后**立即**按 [04_critic_review.md](04_critic_review.md) 切换审稿视角自查,修复"必须修改"项。审稿-修订最多 2 轮。

## Step 5:迭代修改与导出 ⏸

1. 展示草稿(渲染后的 Markdown),邀请用户提修改意见,逐轮修订。
2. 修改涉及新数字时,回到统计 JSON 核实;统计中没有的数字必须由用户亲口提供。
3. **⏸ 用户确认定稿**后写出文件:`runs/<今天日期>/resume_<公司或职位>.md`。
4. 询问是否删除 `<!-- src -->` 溯源注释(投递版建议删除,存档版建议保留)。

## 归档(每轮运行结束时执行)

把本轮的中间产物存入 `runs/<今天日期>/`:`stats.json`、画像 JSON、职位列表、每版简历草稿、用户的修改意见摘要,以及一个 `meta.json` 记录 `{"model": "<本次使用的模型>", "date": "...", "target_job": "..."}`。这些数据是阶段 B 评测集的原料。

## 事实清单规则(全程最高优先级)

1. `stats.json` 是唯一事实来源。简历中的每个数字必须能在其中找到出处,或由用户亲口提供。
2. 禁止编造:用户量、性能百分比、营收影响、团队规模——统计里没有的一律不写,需要时问用户。
3. 每条项目 bullet 带 `<!-- src: 仓库, 依据 -->` 注释。
4. 多人仓库对照 `author_share` 描述个人贡献,不把团队成果归于个人。
5. 拿不准就问用户,不要替用户"美化"。
